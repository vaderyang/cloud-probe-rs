# 100 GbE capture backend benchmark — DPDK pdump vs AF_PACKET

Real-hardware comparison of the two cpworker capture backends in this port, on
the 100 GbE Mellanox ConnectX‑6 Dx link between **laojun** (`10.2.0.12`,
traffic generator) and **yinjiao** (`10.2.0.11`, capture host).

- **AF_PACKET** — the `libpcap` capturer type is implemented as an
  `AF_PACKET` socket (`crates/cpworker/src/capturer/af_packet.rs`), now backed by
  a **`TPACKET_V3` `PACKET_RX_RING` mmap** (with a `recvmsg`-per-packet fallback).
  It is **not** libpcap itself.
- **DPDK pdump** — an external DPDK primary (`verification/dpdk/primary.c`,
  `rte_pdump_init()` + `rte_eth_rx_burst`) plus cpworker as a DPDK secondary that
  drains the pdump ring (`crates/cpworker/src/capturer/dpdk_pdump.rs`), DPDK 25.11.

## Method

Frames: 64 B Ethernet, valid UDP (`10.2.0.12:49000 -> 10.2.0.11:49001`),
generated by `dpdk-testpmd --forward-mode=txonly --txonly-multi-flow` on a
laojun SR‑IOV VF (`0000:46:00.1`) at the yinjiao VF MAC. Offered load is swept
by the number of TX queues/cores (1/2/4).

Ground truth is the **physical-port counters** on both ends:

- offered  = Δ`tx_packets_phy` on laojun `ens72np0`
- wire     = Δ`rx_packets_phy` on yinjiao `ens8np0`
- captured = Δ`cap_packets` from `cpctl -u <sock> stats`
- CPU      = Δ(`utime`+`stime`) of cpworker / primary over the window

Ethernet PAUSE is disabled on both ends for the duration (otherwise receiver
congestion back-pressures the generator and caps the offered load).

## Results (64 B frames, ~9–10 s windows)

| backend | offered Mpps | wire Mpps | captured Mpps | cap % of wire | cpworker CPU | primary CPU |
|---|---:|---:|---:|---:|---:|---:|
| AF_PACKET | 29.8 | 29.8 | **0.474** | 1.59 % | 9.27 s / 9.28 s (100 %) | — |
| AF_PACKET | 59.6 | 59.5 | **0.471** | 0.79 % | 9.31 s (100 %) | — |
| AF_PACKET | 139.2 | 131.5 | **0.468** | 0.36 % | 9.26 s (100 %) | — |
| DPDK pdump (ring 2048) | 28.3 | 27.7 | **4.26** | 15.4 % | 4.85 s (47 %) | 10.35 s (~1 core) |
| DPDK pdump (ring 2048) | 56.8 | 57.7 | **4.37** | 7.6 % | 3.96 s (40 %) | 9.79 s |
| DPDK pdump (ring 2048) | 132.2 | 132.2 | **3.70** | 2.8 % | 3.32 s (35 %) | 9.44 s |
| DPDK pdump (ring 65536) | 29.9 | 30.0 | **5.87** | 19.6 % | 5.08 s (54 %) | 9.41 s |

## Findings

1. **AF_PACKET saturates at ~0.47 Mpps** and stays there regardless of offered
   load, burning **100 % of one core**. It is syscall/compute-bound: the
   `recvmsg`-per-packet design costs ≈2.1 µs/pkt. Captured fraction collapses
   from 1.6 % → 0.36 % as load rises.
2. **DPDK pdump saturates at ~4.3 Mpps** (≈**9×** AF_PACKET) with only
   **35–55 %** of cpworker's CPU. At the same offered load the ratio is ~15–20 %.
3. The pdump ceiling here is set by the **primary's single-RX-queue + per-packet
   clone** path (the primary is ~100 % of one core), not by cpworker's ring
   drain. A production primary with multiple RX queues/lcores should raise it.
4. **pdump `ring_size` matters**: 65536 descriptors gave +38 % (4.26 → 5.87 Mpps)
   at the same offered load versus the 2048 default.
5. **Neither backend reaches 100 GbE line rate** for 64 B frames (~148 Mpps) in
   this single-cpworker-thread configuration. Total CPU cost: DPDK ≈1.5 cores
   (primary + secondary) vs AF_PACKET ≈1 core.

## Caveats

- 64 B-frame flood is the harshest case; larger frames shift both curves.
- The DPDK primary was the minimal single-queue `primary.c`; multi-queue
  primaries and multiple cpworker tasks were not tested.
- Measured on kernel 5.15 with DPDK 25.11, `--iova-mode=va`, bifurcated mlx5
  (kernel netdev kept up during the DPDK runs).

## AF_PACKET ring improvement (cloud-probe-rs-c7o)

`af_packet.rs` originally read **one frame per `recvmsg` call**. A `perf` profile
of the 64-byte flood put ~94% of the capture CPU inside `packet_recvmsg` (skb
copy + skb free + the socket lock) — that, not userspace, is what capped it at
~0.47 Mpps.

The capturer now sets up a **`TPACKET_V3` `PACKET_RX_RING` mmap** after the bind
and drains whole blocks per `capture_once`; it falls back to `recvmsg` if the
kernel rejects the ring, or on loopback when the outgoing copy still has to be
filtered in userspace. Same 64-byte flood (~117–135 Mpps on the wire):

| version | captured | cap % of wire | cpworker CPU |
|---|---:|---:|---:|
| `recvmsg` (before) | 0.47 Mpps | 0.36 % | 100 % |
| `TPACKET_V3` ring (after) | **2.5 Mpps** | 1.9 % | **~7 %** |
| `tcpdump` / libpcap V3 (reference) | 1.93 Mpps | — | — |

- **~5× more frames captured, ~14× less process CPU.**
- The ring is **faster than libpcap's own `TPACKET_V3`** (2.57 vs 1.93 Mpps at the
  same offered load). The residual loss is the kernel/NIC interface
  (`rx_out_of_buffer`, tcpdump's "dropped by interface"), not the capturer.
- Going further needs `PACKET_FANOUT` with one socket per NIC RX queue: a single
  `AF_PACKET` socket serialises on the ring block lock (adding RX queues did not
  help — 4 queues stayed at ~2.45 Mpps).

## Practical notes / pitfalls

- The symptom "testpmd transmits N packets but tcpdump sees 0" is **not a wire
  drop**: (a) `testpmd TX-total` includes `TX-dropped`; (b) frames sent to a VF
  MAC land on the VF, not the PF; (c) when a DPDK primary owns the RX queue the
  kernel cannot see it at all. Use physical-port counters as ground truth.
- **Ethernet PAUSE must be off** (`ethtool -A <if> autoneg off rx off tx off` on
  both ends) or receiver congestion throttles the generator (70.7 → 123.9 Mpps
  measured when disabled).
- testpmd needs ≥2 lcores (master + forward) and `--txq`/`--nb-cores` set to use
  more than one TX queue; `--no-huge -m 4096 --total-num-mbufs=131072` on hosts
  without hugepages.
